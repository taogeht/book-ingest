curriculum-ingest

A single-operator webapp that extracts structured curriculum data from textbook PDFs and produces an exportable bundle suitable for seeding a new LMS instance.

01Phase 1 scope #

The slice that's shipped today. Anything not listed here is intentionally deferred — see Phase 2 priorities.

  • Digital PDFs (Marker handles them natively; scanned PDFs work opportunistically via Marker's built-in Surya OCR but aren't an explicit target).
  • Layout-aware text extraction via Marker (Python subprocess) + page-image rendering via pdftoppm at 150 DPI.
  • Vision-LLM fallback (Claude Sonnet 4.6 with image input) for low-text pages and picture-word grids — the layouts where Marker alone misses the point.
  • Vocabulary extraction only — no reading passages, no grammar focus.
  • One source document per project.
  • LLM-driven unit detection + vocabulary extraction (Claude Sonnet 4.6).
  • Review UI: approve / reject / toggle multi-word / edit POS via dropdown.
  • Export to .bundle.zip containing manifest.json, curriculum.json, vocabulary.json.

04Auth model #

Auth is intentionally minimal — this is a tool for one operator. No user accounts, no sessions table.

  • Password lives in the INGEST_PASSWORD env var.
  • POST /api/login constant-time compares the submitted password against that env var.
  • On success a 32-byte random token is generated, hashed with SHA-256, and stored as system_settings.session_token_hash.
  • The token (cleartext) is sent back as an HttpOnly cookie ingest_session.
  • Middleware redirects every /projects/* and protected API route to /login when the cookie is missing. Route handlers re-validate the hash on every authenticated request.
Note Rotating INGEST_PASSWORD doesn't auto-invalidate existing sessions. To force re-login, call POST /api/logout or delete the session_token_hash row in system_settings.

05Pipeline #

Triggered fire-and-forget from POST /api/projects/[id]/upload after the PDF lands in R2. Stages 1 and 2 run concurrently; 3 starts after both finish.

  1. Page-image rendering · pdftoppm Every page → PNG at 150 DPI, uploaded to R2 at ingestion-pages/{project_id}/{source_doc_id}/page-{n}.png. Fast (~100 ms/page). Storage keys land in extracted_pages.page_image_key.
  2. Text extraction · Marker marker_single --output_format json as a subprocess. Output is parsed into per-page raw_text (reading-order concatenation) and layout_json (the full Marker block tree with image blobs stripped). Slow (~10–30 s/page on CPU).
  3. Vision fallback · Claude Sonnet 4.6 + image Triggered per page when Marker yielded <50 chars, when the page is figure-heavy (≥4 picture blocks + <30 words — typical picture-word grid), or when Marker failed on that page. The page PNG is sent to Claude with a prompt to extract labels and classify the page (vocabulary_grid | reading_passage | exercise | dialogue | other). Vision-derived text replaces the Marker text on that row; extraction_method becomes vision or marker+vision.
  4. Unit detection Claude receives all page snippets (first ~200 chars each) and returns JSON { units: [...] }. Validated with Zod, persisted to detected_units.
  5. Vocabulary extraction For each detected unit, full page text + page_type annotations are sent to Claude. vocabulary_grid pages are trusted aggressively; reading_passage pages are excluded unless they carry an explicit vocab callout. Persisted to extracted_vocabulary.

All LLM responses are persisted with their confidence and free-text reasoning so the review UI can surface why the model picked what it did. extracted_pages.extraction_method records which combination of Marker + vision produced each page's text.

Re-runnable Two scripts re-run individual stages on demand without re-uploading: npm run reextract-doc <sourceDocumentId> -- --confirm wipes and re-runs Marker + vision; npm run reextract-vocab <projectId> -- --confirm wipes and re-runs only the vocab prompt against existing pages. Use these while iterating.

06Review UI #

/projects/[id]/review exposes three tabs:

  • Source documents — status of each uploaded PDF and any parse_error.
  • Units — detected units with confidence + LLM reasoning. Toggle reviewed.
  • Vocabulary — table filterable by unit. Approve / reject per row; toggle multi-word; edit POS via dropdown.
Scope Inline editing of the word itself and re-assigning a row to a different unit are deliberately not in Phase 1 — toggle-style review is enough to validate the pipeline.

07Export bundle #

/projects/[id]/export enforces two readiness conditions:

  • Every detected unit is marked reviewed.
  • At least 80 % of vocabulary rows are approved.

When ready, Generate bundle creates a ZIP at ingestion-bundles/{project_id}/{ts}.bundle.zip and returns a 24-hour signed URL. Project status moves to exported.

Bundle layout:

manifest.json     # version, project metadata, source-doc info, counts
curriculum.json   # curriculum name, level, language, units
vocabulary.json   # array of approved vocab entries with unit_number / source_page

08Deployment (Coolify) #

1 · Repo + Coolify application

  • Push to GitHub (already done: taogeht/book-ingest).
  • Coolify → New Resource → Application → Public Git repository.
  • Build Pack: Dockerfile.
  • Domain: ingest.mschool.com.tw — Coolify provisions the Let's Encrypt cert.

2 · Database (shared Postgres, dedicated DB + role)

Reuse the existing recording-app Postgres instance. Connect as a superuser and run:

CREATE DATABASE curriculum_ingest;
CREATE ROLE ingest_app WITH LOGIN PASSWORD 'pick-a-strong-one';
GRANT ALL PRIVILEGES ON DATABASE curriculum_ingest TO ingest_app;

-- Connect to the new DB to grant schema-level privileges:
\c curriculum_ingest
GRANT ALL ON SCHEMA public TO ingest_app;

Then DATABASE_URL=postgresql://ingest_app:pick-a-strong-one@<recording-app-postgres-host>:5432/curriculum_ingest.

One Postgres container, one backup job, one thing to monitor. The two databases are isolated — ingest_app can't touch the recording-app DB. The only shared resource is the connection pool, fine for a single-user LLM tool.

Escape hatch Want full isolation later? Spin up a second Postgres service in Coolify and point DATABASE_URL at it. Schema is drizzle-kit push --force'd on boot, so migrating is pg_dump → restore → swap env var. No code changes.

3 · R2 bucket

Create a new bucket curriculum-ingest-sources. Reuse the existing R2 API credentials from recording-app.

4 · Environment variables

DATABASE_URL=postgresql://ingest_app:...@<pg-host>:5432/curriculum_ingest
INGEST_PASSWORD=<strong password — the only thing protecting the tool>
R2_ACCOUNT_ID=...
R2_ACCESS_KEY_ID=...
R2_SECRET_ACCESS_KEY=...
R2_BUCKET_NAME=curriculum-ingest-sources
R2_PUBLIC_URL=https://<accountid>.r2.dev/curriculum-ingest-sources
ANTHROPIC_API_KEY=sk-ant-...
NEXT_PUBLIC_APP_URL=https://ingest.mschool.com.tw

5 · Resource sizing

  • Memory: at least 6 GB allocated to the container. Marker uses ~4 GB during inference, the rest goes to Node + headroom. The 2 GB Hetzner CX11 will OOM.
  • Disk: image is ~5 GB. The model cache lives in the image (pre-warmed at build), so no extra volume is needed.
  • CPU: Marker runs on CPU (no GPU support assumed). Expect ~20 s/page on a modern x86 core; a 100-page textbook takes 30–40 min end-to-end.

6 · Deploy

The container's npm start runs drizzle-kit push --force && next start, so the schema is applied on every boot — no migration choreography. First build is slow (PyTorch + model download); subsequent builds are cached if you don't touch requirements.txt.

09AF&F Book 1 test plan #

The first regression target is American Family & Friends Book 1; we have a known-good 379-entry vocabulary table from the recording-app.

  1. Sign in to ingest.mschool.com.tw with INGEST_PASSWORD.
  2. Create a new project: name AF&F Book 1, curriculum American Family and Friends, target level 1.
  3. Upload the digital PDF of Book 1.
  4. Watch source_documents.status. It should transition uploaded → parsed within ~30 s.
  5. Navigate to /projects/[id]/review:
    • Units tab: AF&F Book 1 has a Starter unit + 9 numbered units + a Goodbye/Review section. Expect 10–11 detected units; off-by-one on start_page is common.
    • Vocabulary tab: count should be in the 300–500 range. Exact match to 379 is not expected — the LLM will include some incidental words and miss a handful.
  6. Spot-check a few units against the known-good list. Approve correct entries, reject obvious mis-extractions.
  7. Need to re-run extraction for a doc? tsx scripts/run-pipeline.ts <sourceDocumentId> (locally with same env).
  8. Once units are reviewed and 80 % of vocab is approved, hit Generate bundle and diff vocabulary.json against the known-good 379.
Acceptance Bundle contains ≥ 300 approved entries that overlap meaningfully with the known-good list. Differences are the operator's problem to reconcile in review.

10Phase 2 priorities #

Ordered by expected value-to-effort after building Phase 1.5 (Marker + vision). Page-image rendering and vision fallback moved up into shipping scope; the items below are what's still on deck.

  1. Page images in the review UI. Images are already rendered to R2 — review just needs a panel that loads the page PNG alongside the extracted text + vision response for that page. Cheapest remaining UX win.
  2. Inline edit of word / unit assignment. Today you can toggle approve / reject / POS but not edit the word itself or move a row between units.
  3. Reading-passage extraction. Separate stage; needs paragraph segmentation and a different prompt. Schema columns to be added.
  4. Direct-to-R2 uploads. Browser PUTs via presigned URL → app records the storage key. Removes the proxy body-size limit (recording-app's Traefik caps at ~50 MB), and any sized textbook becomes uploadable.
  5. Cross-unit deduplication. Spiral curricula re-introduce words; flag "first appearance" vs "recurring."
  6. CEFR auto-tagging. Claude assigns A1/A2/B1 per entry; expose a calibration step. Field is already nullable.
  7. Multi-document projects. Some curricula ship as multiple PDFs (student book + workbook); schema supports many source_documents per project, but unit-detection prompt would need to merge across docs.
  8. Job queue. Currently fire-and-forget from the upload route. With Marker's 30-min runs this matters more: a failed pipeline run requires manual re-trigger via npm run reextract-doc. A tiny pg-backed queue with retries would help.
  9. GPU inference. Marker on CPU is the dominant latency. A GPU node (T4 / equivalent) drops a 100-page textbook from ~30 min to ~3 min. Only worth it if ingest volume goes up.

11Operational notes #

  • All pipeline state is in Postgres. R2 stores binary artifacts (source PDFs, per-page PNGs, export bundles) only.
  • Schema is auto-applied on boot via drizzle-kit push --force. In production you'd normally use generated migrations, but for a single-operator tool the friction isn't worth it.
  • system_settings is currently used only for session_token_hash. Future config (LLM temperature overrides, default target levels, etc.) can land there without a migration.
  • Logs go to stdout — Coolify's log viewer is fine for v1.
  • Marker model pre-warm: ~2 GB of weights are baked into the Docker image at build time. If a future marker-pdf bump changes the model-load API, the pre-warm step in the Dockerfile falls back silently (|| echo ...) and the first ingest just downloads weights lazily.
  • R2 page-image storage: ~200 KB per page × ~100 pages/textbook = ~20 MB per book. Negligible.
  • Vision-fallback cost: ~$0.01–0.03 per page hit. AF&F Book 1 triggers vision on roughly 20–40 pages = ~$0.50–1 per ingest. Set a small budget alert in Anthropic Console if running many books.
  • Re-running stages: use npm run reextract-doc <sourceDocumentId> -- --confirm for pages, or npm run reextract-vocab <projectId> -- --confirm for vocab only. Both print what they're about to delete and refuse to act without --confirm.
